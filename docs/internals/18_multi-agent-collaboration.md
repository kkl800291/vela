# Multi-Agent Collaboration Architecture (Vela Collaboration v2)

本文档定义 Vela 多代理开发与审查协作的权威架构与开发思想。所有相关后端服务、MCP 工具、Provider 编排指引与前端交互均须遵守本文档确立的边界与不变量。

> 精炼版架构铁律已同步写入仓库根目录的 [`AGENTS.md`](../../AGENTS.md)（`CLAUDE.md` 通过 `@AGENTS.md` 自动继承）。

---

## 1. 产品定位与设计哲学

Vela 的多代理协作不是「重型多关卡工单审批流」，而是面向真实工程体验的 **「Tech Lead + 并行开发团队」** 模型：

- **认知聚焦，拒绝会话爆炸**：用户全程只面对 **1 个主对话**（主控兼唯一审查官）。并行开发代理在后台隔离干活并按需折叠查看；常规代码审查与连续多轮讨论不产生一堆一次性临时对话。
- **并行生产，串行审查**：允许指定多个开发子代理在不同隔离 worktree 中并行推进（可选统一开发模型或按任务分配模型），但审查必须严格按照**工程门禁通过并冻结快照的完成顺序**，由同一个主控依次逐个审查，避免并发唤醒、插话竞争和上下文错乱。
- **隔离集成，单次交付**：审过即自动串行集成到系统受管的隔离交付工作区并立即解锁下游，不在中途反复打断用户点确认，也不在用户编辑时零碎改写目标工作区；整批组合验证通过后，用户从汇总 Diff **一次确认应用**。
- **单引擎跨入口一致**：无论用户从主聊天框直接发起，还是从右侧协作面板发起，底层共享同一套持久化协作引擎、同一张实时协作卡与同一条可恢复的 FIFO 审查队列。

## 2. 六条核心架构铁律

以下六条为不可违反的设计不变量（与 [`AGENTS.md`](../../AGENTS.md) 保持一致）：

1. **主控负责裁决，解耦「上下文洁净度」与「对话数量」。** 每个协作计划由当前主线程统筹，开发代理在独立受管 worktree 中并行执行；持续多轮讨论与开发返修复用既有线程；日常逐步审查在主线程内按 FIFO 依次完成（开发代理与主控天然实现作者/审查者分离）；新鲜上下文冷眼审计保留给「交付前可选单次整批终审」或显式触发的高风险二审，结果折叠进协作卡并交回主控裁决，不以零散临时对话污染侧边栏。
2. **审查绑定不可变证据。** 门禁、审查裁决、串行集成与最终交付必须通过冻结的不可变 Git 工作区快照建立可追溯绑定。任何环节若导致有效改动变化，必须重新过门禁并重新获取裁决；严禁以活动 worktree 或实时 `HEAD` 作为集成或交付来源。
3. **协作消息排队且可恢复。** 主控协作信箱按持久化顺序投递，每个主线程至多拥有一个活跃协作项；系统唤醒必须通过队列投递（严禁 `auto` 插话或提升为 steer），并使用稳定身份与受验证的专属 `runId` 绑定；状态迁移、回执与待执行意图先在事务内提交，外部副作用随后执行并在启动时对账。
4. **隔离集成，用户确认交付。** 仅通过主控裁决的不可变改动可进入隔离集成区，下游依赖仅在上游集成对账完成后解锁；整批组合验证通过后由用户显式确认一次应用到目标工作区，保留用户真实 Git index 与已有编辑；严禁自动 `git commit` 或 `git push`。
5. **故障沿依赖传播，不阻塞全局。** 集成冲突、决策挂起、返修超限、证据异常或主控回合漏交结论，仅暂停受影响步骤及其下游，立即释放审查队列与集成通道，无关并行任务继续推进；任何恢复或撤回操作须拒绝过期证据并保留用户手工编辑。
6. **服务端拥有协作状态。** 聊天与右栏共享服务端持久化状态机与轻量投影；客户端只渲染投影状态，大体积 Diff 与快照文件内容通过只读工具按需分页读取，Provider 差异隔离在适配器边界。

## 3. 角色模型、会话拓扑与上下文治理

### 3.1 双角色体系

默认路径严格收敛为 **2 个角色**，不引入常驻第三角色（全局独立审查官），也不区分「技术复查」与「产品验收」双关卡：

| 角色 | 承载实体 | 职责边界 |
|---|---|---|
| **主控 / 审查官（Orchestrator）** | 当前主对话线程（`parentThreadId`） | 拆解计划、回答开发代理的技术/契约升级、按 FIFO 依次审阅冻结快照（一次完成技术质量与需求对齐核查）、决定通过或打回返修、主持最终交付汇报。 |
| **开发代理（Dev Worker）** | 每任务步的独立子线程（`childThreadId`） | 在独立受管 worktree 内编码、自测、响应主控打回返修或冲突解决；返修与冲突解决优先复用原 `childThreadId` 上下文。 |

- **模型指定**：主控固定使用当前主对话所选模型；开发代理可在启动计划时指定默认开发模型（或按步骤单独覆盖），未指定时继承主控模型。切换默认开发模型不得覆盖单步显式配置。
- **两级互补审查（融合「单主控过程审」与上游「新鲜上下文防偏见」优势）**：
  - **四类协作活动的上下文与会话边界**（将「UI 对话拓扑」与「模型上下文洁净度」解耦，不搞一刀切）：

| 协作活动 | 是否需要连续历史 | 上下文与会话策略 |
|---|---|---|
| **并行开发与返修 / 解冲突** | 需要 | 独立受管 worktree 子线程并行执行；返修与冲突解决复用原 `childThreadId`。 |
| **同一议题多轮方案讨论** | 需要 | 复用既有讨论线程，禁止每轮重开孤立对话并重复倾倒背景。 |
| **过程逐步审查** | 需要全局需求与跨步契约 | 同一主控在主线程按 FIFO 依次审冻结快照（开发子代理写代码 ≠ 主控审代码，天然作者/审查者分离），零新增审查对话。 |
| **交付前冷眼终审 / 单步高风险二审** | 刻意隔离过程噪音（防锚定偏见） | 仅针对冻结快照发起干净上下文只读审计（若因补修触发复审，仍以干净上下文携带 `brief / findings / objections`）；结果归回协作卡内联折叠，最终裁决权仍归主控。 |

- **交付前可选单次冷眼终审（Batch Fresh-Eye Audit）**：将上游最宝贵的“新鲜视角”从每步每轮 N 次碎片盲审，收敛到最高杠杆的单一节点——整批集成并通过 `batchGates` 后，针对最终汇总快照 `base..delivery` 可选执行 **1 次** 干净上下文只读终审（支持同模型干净上下文或指定异构模型），专门捕获跨模块组合漏洞与主控长上下文疲劳/盲区；审出真实 blocker 时交回主控裁决并派对应开发代理修补。
- **按需单步二审（Second Opinion）**：某一步存在高风险架构疑点时，用户或主控仍可对该步的**同一个冻结 `reviewId`** 显式触发一次性干净上下文只读复核；结论同样折叠进协作卡并交回主控裁决。
- **规划前盲审与逐步人工确认**：移出默认流程，仅作为显式高级入口保留，不占据默认界面与配置项。

### 3.2 会话降噪与连续讨论复用

- **左侧边栏**：协作派生的开发子线程归属在主线程之下，默认折叠收纳，不平铺污染主会话列表；主线程仅在存在待人类处理项（决策/升级/超限）或整批可交付时展示轻量提醒徽章。
- **主对话时间线**：只保留 **1 张实时协作卡**、需要人类拍板的升级消息与最终交付汇报。常规系统队列唤醒与逐项审查回合在投影层归属并折叠进协作卡（可随时展开查看完整推理与证据），避免刷屏成日志墙。
- **Provider 编排指令对齐（`packages/provider-core/src/server/orchestrationInstructions.ts`）**：
  - 多代理开发 + 同一主控依次审查统一接入 Vela 协作引擎，禁止回退到“每审一步新开 `delegate_task`”。
  - “每次 review/re-check 新开 `delegate_task`” 的约束严格收窄为**显式委派独立外部审查**；连续多轮方案讨论或同一角色的常规审查复用既有会话上下文。

### 3.3 主控上下文膨胀与压缩恢复

- **唤醒载荷极简**：投递给主控的审查消息只包含 `planId`、`stepId`、`reviewId`、轮次、短目标、稳定条目 ID 的验收标准与门禁结果摘要，绝不内联大体积 patch。
- **按需取证**：主控通过只读证据接口按文件分页读取 Diff 与快照行区间。
- **Compaction 无损续审**：原始需求、验收标准、已集成摘要、历史裁决与当前 `reviewId` 证据均由服务端持久化；即便主对话发生上下文压缩，主控仍可通过只读工具完整恢复审查上下文。

## 4. Git 工作区快照、隔离集成与单次交付

本节解决多代理并行开发下「主控在主工作区、开发在各自 worktree、审过内容与合入内容必须 100% 一致」的核心工程难题。

### 4.1 仓库绑定与快照边界

- 每个协作计划绑定 `(environmentId, canonicalTargetWorktree, gitCommonDir)`。
- **Git 工作区快照**通过临时 `GIT_INDEX_FILE` 生成不可变 tree 与合成提交对象（使用合成 author/committer 环境变量，不依赖用户 git 配置），**全程不触碰用户真实分支、`HEAD`、真实 index 或 reflog**：
  - 按原 `HEAD` 与真实 index 的并集识别已跟踪路径，从磁盘读取实际工作区内容，同时纳入未忽略的新建文件。
  - `.vela/` 与 `.harness/` 在建树和生成变更清单时均显式排除（含已被跟踪的条目）。
  - 任意 Git 子命令失败均立即中止捕获并显式报错，绝不静默产出空 diff。
- **非 Git 目录与 Unborn 仓库**：
  - 非 Git 目录仅允许执行只读调研（`research`）与决策（`decision`）步骤，不支持隔离集成写操作。
  - 无初始提交的 unborn 仓库使用无父合成提交启动快照链。

### 4.2 首版 Git 能力矩阵与硬性约束

- **Git 版本要求**：v2 写入计划要求 Git >= 2.38（具备 `git merge-tree --write-tree` 能力）。为兼容 Git 2.38（尚未引入 `--merge-base` 标志），三方合并统一将当前集成树与候选树包装为**以指定步骤基线为共同父提交的临时合成提交**后再调用 `git merge-tree --write-tree`。低于 2.38 的环境在启动写入计划前直接返回明确的能力错误。
- **特殊条目处理规则**：
  - **子模块（Submodule）**：仅保留干净且已固定的 gitlink；阻止脏子模块、gitlink 变更与嵌套 Git 仓库进入交付。
  - **二进制文件**：按大小预算、对象 OID 与变更类型（A/M/D）呈现，不倾倒乱码 diff；双方同时修改即判冲突。
  - **符号链接（Symlink）**：按链接条目本身捕获与比对；应用到目标工作区时严禁穿越符号链接父路径写入目标目录之外。
  - **显式拒绝项**：首版拒绝稀疏检出（sparse-checkout）、大小写不敏感文件系统上的路径大小写碰撞、无法无损物化的条目，以及受自定义 smudge/clean filter 或 merge driver 影响的路径。

### 4.3 隐藏引用命名空间与生命周期

沿用 [`01_architecture.md`](./01_architecture.md) 中「隐藏 Git refs 保护快照、绝不污染用户分支」的原则，所有协作快照使用隐藏引用保存提交 OID（保证 `git gc` 不回收、服务重启可读）：

```text
refs/vela/collab/<planId>/base                              # 启动时目标工作区快照（含用户已有未暂存改动）
refs/vela/collab/<planId>/integration                       # 当前隔离集成区最新提交（初始等于 base）
refs/vela/collab/<planId>/delivery                          # 整批组合验证通过后的冻结交付提交
refs/vela/collab/<planId>/steps/<stepId>/r<attempt>/base    # 该步骤该轮执行基线提交
refs/vela/collab/<planId>/steps/<stepId>/r<attempt>/reviewed# 该步骤门禁通过后冻结的受审快照提交
```

- **引用与目录回收**：活动证据与可撤回交付记录随计划历史保留；清理严格依据持久化的所有权与引用关系执行。仅自动回收已释放且工作树干净的受管 worktree，含未归档本地改动的脏目录予以保留并可定位。
- **推送隔离**：Vela 自身所有推送路径排除 `refs/vela/collab/*`；需注明外部手工执行 `git push --mirror` 时 Git 默认会携带自定义 refs。

### 4.4 锁定门禁输入 → 冻结受审证据 → 串行集成

1. **门禁输入锁定**：开发子代理回合及关联文件写入完全结束后，先捕获 `candidateCommit`，在隔离检出上执行路径边界审计与 Hard Gates。门禁全部通过且复核受控树与 `candidateCommit` 一致后，才固化 `reviewed` ref 并发布不可变 `reviewId`（绑定 `stepBaseOid`、`reviewedOid`、验收标准版本、门禁摘要），随后入 FIFO 审查队列。
2. **只读快照取证**：主控审查 `reviewId` 时，服务端直接从 `stepBaseOid..reviewedOid` 提供变更清单、单文件分页 diff 与快照行区间读取，彻底避免主控因 CWD 位于目标工作区而读到旧文件。
3. **串行集成与「有效清单变化」复审规则**：
   - 主控批准 `reviewId` 后，步骤进入计划级串行集成通道。
   - 使用三方合并将 `(stepBaseOid -> reviewedOid)` 合入当前 `integration`。
   - **关键一致性校验**：即使 Git 三方合并无文本冲突，也必须逐路径对比本次合并对 `integration` 实际引入的 `(oldBlob/mode -> newBlob/mode)` 有效变更清单与已审清单是否完全一致：
     - **完全一致**：使用条件更新（`git update-ref <ref> <newOid> <oldOid>`）推进 `refs/vela/collab/<planId>/integration` 并同步隔离集成工作区，对账后提交步骤为 `integrated`，随即解锁下游依赖并固定下游启动 OID。
     - **无冲突但有效清单变化**（例如上游已改同一文件导致合并后结果不同于受审版本）：**禁止静默推进集成！** 将合并候选树重新过门禁、冻结新 `reviewId` 并排入 FIFO 队尾，由主控再次确认。
     - **存在实际冲突**：不污染隔离集成区；以冲突发生时的最新 `integration` OID 开出新的修复受管 worktree，保留旧 worktree 及其本地状态，通过带 `expectedWorktreePath` 的线程工作区切换与排队续跑继续复用原 `childThreadId` 解决冲突，完成后重过门禁并排到 FIFO 队尾复审。

### 4.5 整批组合验证、单次安全交付与三方撤回

- **整批组合验证与可选冷眼终审（`batch_verifying`）**：全部步骤达到 `integrated` / `done` 后，固定当前 `integration` OID，在隔离集成工作区按拓扑顺序执行去重聚合后的 `batchGates`（或计划显式指定的整批验证命令），专抓单步全绿但跨步破坏调用链的组合回归。
  - 若 `batchGates` 失败：计划回到 `running` 并向主控信箱投递批次级升级（保留已集成步骤）；主控可针对该 OID 显式重试或追加修复步骤（走同一套门禁→审查→集成流程）。一旦计划版本或 `integration` OID 变化，旧的批验结果、冷眼终审结论与交付授权立即作废。
  - 若 `batchGates` 通过且启用了**交付前冷眼终审（Batch Fresh-Eye Audit）**：针对冻结的 `base..integration` 汇总快照运行 **1 次** 干净上下文只读审计（审计报告折叠归入协作卡，不平铺为侧边栏新对话）；无阻塞级问题则放行，存在阻塞级发现则通过主控信箱交由主控裁决是否退回 `running` 补修。
  - 最终通过后冻结 `refs/vela/collab/<planId>/delivery`，计划进入 `ready_to_deliver`，唤醒主控输出最终汇总汇报。
- **单次安全应用到目标工作区（`applyDelivery`）**：
  - 仅由用户显式操作触发，绑定 `(deliveryId, expectedTargetState)`，在目标工作区持久化占用锁下执行。
  - 先用冻结的 `base -> delivery` 对目标工作区当前内容做隔离三方预检：
    - 若与用户启动后的手工编辑冲突：**零写入**，清晰列出冲突文件；
    - 若目标工作区漂移导致三方合并产生新的组合结果：先对该组合结果重新验证并向用户呈现更新后的可确认版本，不盲目写入；
    - 写入前先持久化逐路径预期值、目标值与恢复记录，写入前逐路径复检，以**未暂存改动**落盘（不改真实 index、不 commit），并持久化 `appliedBaseTree` 与 `appliedResultTree`。
  - 工作区锁仅协调 Vela 内部写入者（含 v1/v2 共用准入）；若遇进程崩溃或外部编辑器并发写入，重启恢复按路径核对：发现既非预期旧值也非预期新值的“第三种内容”时，立即停止自动恢复并完整保留现场交由用户处理。
- **整批安全撤回（`revertDelivery`）**：以 `appliedBaseTree -> appliedResultTree` 做整批三方逆向合并，保留用户在应用之后的后续手工编辑；遇重叠先报冲突而不覆盖磁盘。

## 5. 状态机、双串行通道与持久化事务边界

### 5.1 Plan 级状态机（`engineVersion: 2`）

```text
draft ──► running ──► batch_verifying ──► ready_to_deliver ──► delivered
             ▲               │
             └───────────────┘ (批验失败回退补修 / 用户更新计划)
（任意非终态可进入 cancelled；致命不可恢复异常进入 failed；全部剩余项等待人类时呈现派生阻塞态）
```

### 5.2 Step 级状态机（11 态，取代 v1 的 17 态）

| 状态 | 含义 | 说明 |
|---|---|---|
| `locked` | 等待前置 DAG 依赖 | 仅上游 `integrated`/`done` 后解锁 |
| `ready` | 已解锁待派发 | 计划处于 `running` 时自动派发，无需逐卡手点 |
| `developing` | 开发代理执行中 | 附 `phase: "initial" \| "repair" \| "conflict"` 与 `attempt` |
| `verifying_gates` | 锁定候选提交并执行门禁 | 隔离检出运行边界审计与 Hard Gates |
| `queued_for_review` | 证据已冻结，排队等主控审 | 持有持久化单调 FIFO 序号与不可变 `reviewId` |
| `reviewing` | 主控正在审查（FIFO 队首） | 绑定专属主控信箱项与 `threadRunId` |
| `integrating` | 串行集成通道处理中 | 仅 `change` 步骤进入；已释放主控审查席位 |
| `integrated` | 已安全集成进隔离交付区 | `change` 步骤终态，触发解锁下游依赖 |
| `done` | 已完成确认 | `research` / `decision` 步骤终态，触发解锁下游 |
| `needs_attention` | 需人工介入/处理 | 带结构化 `attentionReason`（见下），不阻塞无关任务 |
| `cancelled` | 已取消 | 同步作废在途 `reviewId` 与未消费唤醒 |

`attentionReason` 枚举：`decision`（决策拍板）｜ `escalation`（升级人类裁决）｜ `gate_failed`（门禁失败）｜ `repair_limit`（达到自动返修上限，默认 2 轮）｜ `conflict_limit`（冲突解决超限）｜ `review_incomplete`（主控回合结束但未提交结论）｜ `evidence_error`（快照/Git 能力异常）｜ `manual_check_required`（审查包含需人工核验项）。

### 5.3 双串行通道解耦（审查通道 vs 集成通道）

- **通道 1：主控串行信箱（Single-Active-Turn Orchestrator Inbox）**
  - 按 `(environmentId, parentThreadId)` 严格保证至多 **1 个活跃协作项**（通过数据库唯一约束保障）。
  - 统一串行承接四类事件：`review`（FIFO 队首）、`orchestrator_escalation`（技术/契约求助）、`batch_verification_failed`（批验失败）、`delivery_ready`（最终交付汇报）。
  - 投递协议：先在事务中持久化 `inboxItemId`、`commandId`、`messageId` 与载荷 → 事务外调用 `sendToThread(..., mode: "queue")` → 依据精确消息与运行投影绑定专属 `runId`。
  - **禁止 Steer 提升**：系统协作消息带有结构化来源标记，服务端编排层禁止将其提升为 `steer`（保护用户正在进行的主控对话回合）。
  - **推进条件**：审查项在**裁决结论已持久化且其专属 `runId` 已终止**后立即释放席位，推进下一项（因此当 S1 审完进入 `integrating` 时，主控可立即开始审 S2，互不等待）。技术升级若转为等待人类拍板，同样立即释放席位。
  - **防死锁与父线程不可达**：若专属 `runId` 正常/异常终止却未提交有效结论，记录 `needs_attention(review_incomplete)` 并立即释放席位推进下一项（面板支持一键重入队）。若父线程已被删除、归档或无法投递，记录可见原因并保留证据，禁止无限重放。
- **通道 2：计划级串行集成通道（Integration Lane）**
  - 严格按审查批准的持久化顺序逐个集成。
  - 遇冲突或有效清单变化时释放通道，原步骤转入冲突返修或重过门禁再排队，不影响后续已批准步骤的集成调度。

### 5.4 中途需求变更与计划版本控制

- 主对话中的普通用户聊天保持自然人类输入语义，绝不隐式改写执行中的计划；只有显式计划更新命令会推进 `planVersion`。
- 计划更新须通过 DAG 校验，仅作废受影响步骤的在途证据、回执与未集成下游，无关并行步骤继续运行。
- 取消尚未集成的步骤时联动处理其依赖者；已集成进隔离交付区的改动若需撤销，通过显式补偿步骤走同一套门禁与审查流程（保证交付历史线性、可审计）。

### 5.5 持久化事务边界与 v1 共存

对齐 [`01_architecture.md`](./01_architecture.md) 的事件/投影与 Outbox 原则：

- **v2 权威状态落入 SQLite**（替代现有 `VelaDispatchStore.ts` 的 `state.json` 临时文件替换与进程内写锁）：
  - 在**同一 SQLite 事务**内提交状态迁移、持久化投影、幂等命令回执与待执行 outbox 意图；事务提交后再执行 Git、线程投递与文件系统副作用。
  - 每个外部副作用携带稳定操作 ID、预期版本与可核对结果；集成引用更新与操作标记采用条件更新并在重启时对账，对账成功前不宣告集成完成。
  - 数据库唯一约束保证「每主线程单活信箱」，持久化操作租约协调「每计划串行集成」与「每目标工作区写入」；进程内 mutex 仅用于优化本机调度。
- **v1 向后兼容**：历史 `state.json` 在途计划继续按 v1 路径收尾与展示；新建默认协作走 v2；v1 与 v2 共用目标工作区写入准入，杜绝跨版本并发写脏工作区。

## 6. MCP 工具契约、客户端投影与界面边界

### 6.1 收敛现有 MCP 工具名（避免工具膨胀）

不额外堆砌冗余 MCP 工具名，沿用现有工具集并按计划 `engineVersion` 分流：

- **`vela_dispatch_plan`**：创建/更新协作计划（v2 默认支持 `autoStart`、计划级 `defaultDevAgent`、`batchGates` 与稳定条目 ID 的验收标准）。
- **`vela_dispatch_status`**：
  - 默认返回轻量协作摘要（计划状态、当前活跃审查、FIFO 队列位次、各步状态与阻塞项），绝不倾倒大 patch。
  - 扩展只读证据查询分支（按显式 `reviewId` 或 `delivery` 查询）：返回变更文件清单、单文件分页 diff、以及直接从不可变快照读取指定行范围的文件内容。所有查询受调用者权限、绑定仓库、快照存在性与字节上限校验，证据缺失时显式报错。
- **`vela_dispatch_acceptance`**：
  - v2 强制要求：`planId`、`stepId`、`reviewId`、`verdict`（`approve | request_changes`）、结构化技术 `findings`、以及按稳定条目 ID 提交的 `criteriaResults`。
  - **安全校验**：服务端通过 `McpInvocationContext` 校验调用确实来自该 `activeInboxItem` 绑定的专属 `runId`（仅匹配 `threadId` 不足以授权）。
  - **判定规则**：`approve` 要求所有验收条目通过且无阻塞级 finding；含 `manual_check` 时转为人工待办提示；同一结论重放返回原回执，过期运行或冲突结论直接拒绝。`request_changes` 立即释放队首并续跑原开发子线程返修（默认上限 2 轮）。
- **`vela_dispatch_step` / `vela_dispatch_escalation`**：保留并适配 v2（支持触发按需 `second_opinion`、重试 `review_incomplete`、以及用户显式交付/撤回操作）。

### 6.2 客户端投影与旧面板取舍清单

客户端严格遵守 **Orchestration stays pure, UI stays dumb**，仅渲染服务端投影：

| 类别 | 现有 Dispatch 面板元素 | v2 处理方式 |
|---|---|---|
| **保留并强化** | DAG 依赖调度、Worktree 自动隔离、路径审计 + Hard Gates、返修复用原 `childThreadId`、升级工单、运行历史 | 作为 v2 核心底座，接入不可变快照与 SQLite 事务 |
| **核心重构** | `acceptStep` 实时重读 worktree 并写回、`wakeParentOrchestrator(mode:"auto")`、单步 diff 预览、内联计划卡 | 改为隔离集成区 + 批验 + 单次交付；信箱改为 `queue` + 专属 `runId`；内联卡升级为唯一实时协作卡 |
| **移出默认路径** | 技术复查与产品验收双关卡、每步每轮新开 Review 子线程、发布后逐卡手动派发、逐步人工确认合入、常驻审查模型下拉、单步复杂 reviewer 表单 | 从默认流程与主界面移除；仅在用户显式需要盲审或逐步人工验收时保留低存在感专门入口 |

## 7. 验收测试矩阵（实现前置准绳）

任何 v2 实现合入前，必须覆盖以下场景的自动化验证：

1. **证据与合并一致性**：门禁通过后活动 worktree 被篡改（证据不受影响）；两并行步骤无冲突合并但有效变更清单变化（触发重过门禁与排尾复审）；S1 集成冲突转原线程新 worktree 解决时 S2 在审查通道继续推进。
2. **队列、信箱与并发安全**：乱序完成按冻结持久化先后严格 FIFO；返修后排到队尾；尝试将系统协作队列消息提升为 `steer` 被服务端拒绝；非专属 `runId` 或过期 `reviewId` 提交裁决被拒绝；重复提交同一裁决幂等返回原回执。
3. **故障与崩溃恢复**：SQLite 提交意图后/线程投递后/Git 引用更新前/交付多文件写入中途分别模拟崩溃重启，验证对账恢复无重复投递、无重复应用、遇到外部“第三种内容”立即停机保现场。
4. **需求变更与整批交付**：运行中途显式更新计划仅失效受影响子图；单步全绿但组合批验失败回退补修后通过；开启交付前冷眼终审时仅看冻结 `base..integration` 快照、发现 blocker 回交主控裁决且在 OID 变化后旧终审立即作废；目标工作区脏文件启动与交付冲突检测；整批撤回保留用户应用后的后续编辑；v1 在途计划不受影响正常收尾。
5. **Git 兼容性矩阵**：unborn 空仓库、低于 2.38 的 Git 版本能力拦截、已暂存新增后又被 `.gitignore` 忽略的文件、二进制文件冲突、符号链接防越界写入、干净与脏子模块处理。
